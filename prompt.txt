
# Final Project

## **UtilityAI — AI-Powered Electricity Billing & Consumption Analytics Platform**

### In one sentence

> A web-based electricity utility platform where customers can view their electricity consumption and bills, make simulated payments, and interact with an AI assistant that analyzes their consumption and answers questions using utility documents and customer billing data.

The important part is that this is **not just a CRUD billing website**.

The project demonstrates:

* Relational database design
* PostgreSQL optimization
* Data integrity
* Customer consumption analytics
* Vector search
* RAG
* AI + database integration
* REST API development

---

# 1. What problem are you solving?

A traditional electricity customer portal mainly shows:

```text
Consumption
Bills
Payments
```

but the customer still has to manually understand the information.

For example, a customer might see:

> July consumption: 245 kWh
> August consumption: 270 kWh
> August bill: ₹2,050

But the system doesn't explain:

> **"Why did my bill increase?"**

or:

> **"How can I reduce my electricity consumption?"**

or:

> **"What are the rules regarding my electricity bill?"**

### Your system solves this by combining:

**Customer utility data + relational database + analytics + AI/RAG.**

So instead of simply displaying data, the system can turn that data into useful information.

# 2. What exactly are you building?

The application has **four main parts**.

### Part 1 — Customer Portal

Customer can:

* Register/login
* View dashboard
* View monthly consumption
* View bills
* View payment history

---

### Part 2 — Billing System

The system stores:

```
Customer
   ↓
Monthly consumption
   ↓
Bill
   ↓
Payment
```

For example:

```
Customer: Rahul

June      210 kWh     ₹1,550
July      245 kWh     ₹1,820
August    270 kWh     ₹2,050
```

Payment is **simulated**. You don't need to integrate a real payment gateway.

---

### Part 3 — Consumption Analytics

The backend calculates things such as:

```
Current consumption
Previous consumption
Percentage increase/decrease
Average consumption
```

For example:

> Your electricity consumption increased by **10.2%** compared with the previous month.

This analysis is primarily done using **backend/database queries**, not by asking an LLM to perform basic arithmetic.

That's an important design decision.

---

### Part 4 — Energy Assist

The customer can ask:

> Why did my electricity consumption increase?

The system combines:

```
Customer's consumption data
+
Relevant utility information
+
LLM
```

to generate the answer.

For example:

> Your consumption increased from 245 kWh in July to 270 kWh in August, an increase of approximately 10.2%. According to the available energy-saving guidelines, reducing prolonged use of high-consumption appliances can help lower your consumption.

# 10. Database integrity

You will use:

### Primary keys

Uniquely identify records.

### Foreign keys

For example:

```
consumption.customer_id
        ↓
customers.id
```

### NOT NULL

Important fields cannot be empty.

### UNIQUE

For example:

```
customer.email
```

### CHECK

For example:

```sql
consumption_kwh >= 0
```

and:

```sql
amount >= 0
```

This prevents invalid data from entering the database.

---

# 11. Indexing

You don't need 20 indexes.

Create a few **meaningful indexes**.

For example:

```sql
CREATE INDEX idx_consumption_customer_month
ON consumption(customer_id, month);
```

Why?

Because a very common query will be:

> Give me the consumption history for customer X ordered by month.

Instead of scanning the entire table, PostgreSQL can use the index to locate relevant records more efficiently.

# 12. Query optimization
Suppose you have:

```sql
ORDER BY month;
```

You can examine the execution plan:

```sql
EXPLAIN ANALYZE
SELECT ...
```


# 13. Transactions

Use a database transaction for payment.

Conceptually:

```
Payment request
      ↓
BEGIN TRANSACTION
      ↓
Create payment record
      ↓
Update bill status
      ↓
COMMIT
```

If something fails:

```
ROLLBACK
```

This is important because you don't want:

```
Payment created
BUT
Bill still says UNPAID
```

The two operations should remain consistent.

---

# 14. Backup

```

      ↓

      ↓

```

This gives you a practical database administration concept without making the project huge.

# 16. Why pgvector?

Instead of introducing another vector database, use:

```text
PostgreSQL
     +
pgvector
```

This is a very good design decision for this project.

Your structured data stays in PostgreSQL:

```
customers
consumption
bills
payments
```

and the document embeddings can also be stored there.

Therefore:

> **One database handles both relational data and vector search.**

# 19. How customer-specific questions work

Suppose the customer asks:

> "Why is my bill higher this month?"

Don't simply send that question to the vector database.

The system first retrieves the customer's structured data:

```
July:
245 kWh

August:
270 kWh

July bill:
₹1,820

August bill:
₹2,050
```

Backend calculates:

```
Consumption increase
= (270 - 245) / 245 × 100
≈ 10.2%
```

Then the AI receives this information.

So:

```
User Question
      │
      ├───────────────┐
      ▼               ▼
PostgreSQL        RAG Search
      │               │
      ▼               ▼
Customer data    Utility information
      │               │
      └───────┬───────┘
              ▼
             LLM
              │
              ▼
          Final Answer
```

This is the **core methodology of your project**.

---

# 20. Why calculate numbers in the backend?

This is an important engineering decision.

Don't ask the LLM:

> "Calculate the percentage increase."

Instead:

```
Backend → calculation
LLM → explanation
```

Why?

LLMs can make arithmetic mistakes.

So:

```
Deterministic operation → Python/backend
Natural-language explanation → LLM
```
